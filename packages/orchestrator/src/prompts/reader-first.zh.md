# 读者优先写作纪律（教学型代码 wiki）

> 移植自 lecture-to-notes 的 `references/reader-first-writing.md`
> （skill: lecture-to-notes，先逐条复制原条目，再做「代码 wiki」语境兼容改写）。
> 原条目的措辞与编号**必须保留**。
>
> 与 humanizer 的分工：humanizer = 「像人写的」（反 AI 腔，60~80 条模式）；
> 本块 = 「**教会了读者**」。两者正交，本块拼在 humanizer **之后**。

## 1. 保护源码事实，再改进散文

动笔前先记录以下边界（写进页面的是**代码事实**，不是你的推断）：

- 接口签名、函数签名、参数与返回值、枚举与常量；
- 调用关系、触发条件、失败模式与错误处理路径；
- 模块边界、分层意图、以及代码里写明的版本行为；
- 「代码当前如何实现」与「为什么这样设计」之间的分界。

**不得**把实现细节写成设计意图、把单次调用路径写成普遍保证、把注释里的 TODO
写成已生效行为。不确定的版本行为显式标注「以当前代码为准」。归因只在它保护
事实边界时使用（如「当前实现里」「以 `X` 为准」），不要每句都加。

## 2. 先搭读者的论证地图

选标题之前，先用一句话回答每个问题：

1. 本页回答读者的什么中心问题？
2. 目标读者已经知道什么（先验概念）？
3. 读完后读者能**解释 / 定位 / 对比 / 决策**什么？
4. 哪些概念必须先讲，因为后面的概念依赖它？
5. 每个主要回答的证据（文件 / 行号）是什么，证据到哪里为止？

把这些答案转成**节问题**。一节存在，是因为读者需要它的答案，不是因为源码
文件恰好分了十个。当后文的解释为先前提供了先验时，调整顺序补齐。

## 3. 把代码读成教学散文

- 去掉无信息的过渡句、重复设问、空洞的铺垫。
- 合并散落在多处的、回答同一个读者问题的解释。
- 让一个具体例子紧贴它解释的机制。
- 保留有教学价值的**设计权衡 / 已知局限**，省略不教人的流程性寒暄。
- 只在类比**确实降低认知负荷**时使用类比，并说明类比在哪里失效。
- 不得添加源码里不存在的例子、动机或背景，除非验证过并明确标为「补充背景」。

## 4. 每段只做一件事

一段教学散文通常承担以下动作之一：

1. 给出答案或论断；
2. 解释机制或推理；
3. 呈现源码证据或可走查的例子；
4. 给出后果、决策规则或边界。

**不要**把四个动作硬塞进同一段：既定义概念、又推导流程、又列举多个结果、
还附带告警时，拆段。当几小段只是用不同词重复同一个意思时，合并。

检查每句的衔接：第一句要为下一句引入的概念铺路。一段要以它的**结果或后果**
收尾，而不是以「这一点很重要」这类泛论收尾。

## 5. 写具体、自然的中文技术散文

- 直接陈述正面命题。「不是……而是……」只在对比能防止真实误解时保留。
- 把「值得注意的是」「这一点非常重要」换成**它后面的那个后果**。
- 先给平实含义，再给缩写、项目标签、阶段编号或内部命名。
- 主语明确、动词具体。解释一个机制时说清它**允许什么 / 改变什么 / 防止什么**。
- 超过约 90 字的中文长句，复审是否有从句堆叠——**这是复审信号，不是禁令**。
- 去掉源码不支持的形容词：「全面」「系统」「显著」「革命性」「鲁棒」，
  除非代码定义或度量了它。
- 段落与句子的节奏自然变化，不要用随口闲扯、第一人称轶事或装饰性比喻
  来制造「人味」。
- 「首先 / 其次 / 最后」「此外」「因此」「这意味着」只在表达**真实顺序或因果**
  时使用，不要当过渡装饰。

## 6. 把证据框成读者能解读的样子

对每个关键接口 / 行为，说清：

1. 它**是**什么（接口签名或入口）；
2. **谁**调用它（调用方）；
3. **什么条件**触发它（触发条件 / 生命周期）；
4. 它的**边界与失败模式**（什么情况下不生效、报什么错）。

三个以上并列项用表格；正文负责解读，表格负责枚举。图表或表格要先在正文里
被提到再出现。不要为了显得专业而编造调用链或数值。

## 7. 为读者开合每一节

每节以**读者问题或它的短答案**开头；先给平实概念，再给实现细节、术语、
边界或例外。

每节以「读者现在**能做什么** / 下一步**看哪页**」收尾——不要罗列本节的小标题，
不要复读开头的论断，不要以「综上所述」收尾。当下一节依赖本节结果时，
把那个依赖写成自然的交接。

页面末尾的综合应该：

- 说清本页让读者能理解或做到什么；
- 串联跨节机制；
- 分清「代码的结论」与「本文的压缩整理」；
- 指出已验证的边界与一个具体的后续问题。

## 8. 分遍修订（单 Agent 内化为一次结构化自检）

完整草稿存在后，原流程跑七遍修订（结构 / 论证 / 源码口吻 / 术语 / 句式 /
证据 / 渲染读）。单次 Agent 运行内不现实，因此**压缩为 polish Agent 的一次
结构化自检**（`polish.mode = 'full'`，见 `wiki/polish.ts`）：

1. **结构**：先验概念在依赖它的内容之前；每节只回答一个问题。
2. **论证**：每段一件事；证据后面跟着含义。
3. **事实边界**：代码事实与本文的整理保持可区分。
4. **术语**：每个术语只用读者语言定义一次，之后一致使用。
5. **句式**：去掉口语碎屑、模糊主语、从句堆叠、机械对比、重复段式。
6. **证据**：复查每个函数名、参数、行号与因果陈述。
7. **渲染读**：从头通读最终落盘的页面，而不是只看改动片段。

短语扫描能找出候选，但**替不了通读**。不要因为一个句子是被动、长、带比喻
或用了问句标题就重写它；只有当含义、逻辑、重点或可读性**确实**改善时才改。

## 读者优先最终清单

- 初读者读完开头，能说出本页的中心问题吗？
- 每节在给出细节前，先回答了一个具体问题吗？
- 技术命名在平实含义**之后**引入吗？
- 每个函数名与强因果陈述都能溯源到代码吗？
- 代码事实与本文的补充整理，边界清晰吗？
- 每段推进了解释，而不是复述吗？
- 过渡跟随逻辑，而不是固定模板吗？
- 密度门加的是**教学内容**，而不是散文或图表填充吗？
- 结尾解释价值与边界，而不是重放全文吗？
